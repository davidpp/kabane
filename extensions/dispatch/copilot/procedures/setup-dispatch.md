---
title: SETTING UP A DISPATCH SKILL
---
A dispatch skill is how a coding session in this project turns an ask into issues on this board and into shipped work. The dispatch extension ships a generic one at {{extension}}/templates/dispatch: SKILL.md and references/ are the skill, except the overlays PLACEHOLDERS.md lists under ## Overlays, which are copied only when an answer selects them. PLACEHOLDERS.md says what fills each {{NAME}} and which questions settle the project's setup.

The project root is your working directory. Read what it says about itself before writing anything: CLAUDE.md and AGENTS.md, the package manifest's scripts and the gate the instructions name, .claude/agents/, any testing constraints, where it keeps decisions, research and docs, how it names branches, worktrees and commits, and whether the recent git log merges locally or through pull requests.

Then settle the questions under ## Questions in PLACEHOLDERS.md. Answer each one from the project's files where they settle it, and note the file that did. When the project already has a dispatch skill, read its ## This project section first and keep every answer it records, so a refresh asks only what it leaves unanswered. Ask the ones that remain in one go: through your harness's own choice prompt whenever it has one, each question's choices as its options and the recommended one first, and in plain text, ending your turn on it, only where it has none. Write nothing until they are answered. {{extension}}/templates/examples/ shows the ## This project section for three setups: one person landing on main, a team on GitHub with pull requests, and goals carried by a steward. The answers fill {{SETUP_ANSWERS}}, each with its source, and select the overlays: copy an overlay only when an answer selects it, and on a refresh an overlay the answers no longer select is removed, which the diff shows. The answers are about the project, not permission to write: the rule two paragraphs down still decides whether you write without asking.

Fill every placeholder from what you read and what the human answered. Only the project's own files count: your harness may also have loaded the human's personal instructions, and those are theirs, not something a project skill should hand to everyone who clones the repo. {{TEMPLATE_STAMP}} takes what `kabane dispatch stamp` prints, run as the kabane that KABANE ON THIS MACHINE names and copied exactly: it records which template the skill was filled from, so never compute it or carry over an older one. When that command fails, report its error, ask the human to reinstall the dispatch extension, and never invent a stamp. Every coding session here will follow the written skill literally, so it must contain no {{, nothing about a project that is not this one, and no convention you inferred where PLACEHOLDERS.md gives a fallback.

Write only under .agents/skills/dispatch/ in the project root, plus the one link below: the rest of the project is the code the issues describe, which stays the coding session's to change. When neither .agents/skills/dispatch/ nor a real .claude/skills/dispatch/ directory exists yet, being asked to set the skill up is the go-ahead: write the files without asking, then show the content of each one, so the human reads what every future session will be told, and say that deleting the directory undoes it. If .agents/skills/dispatch/ already exists, show the diff and write nothing without an explicit yes, because it may hold their own edits. Codex, Pi, opencode and Gemini read .agents/skills/; Claude Code reads only .claude/skills/, so it reaches the skill through a relative symlink: .claude/skills/dispatch pointing to ../../.agents/skills/dispatch. Create that link when the project root already has a .claude/ directory or the human asks for it; otherwise say in your report that `ln -s ../../.agents/skills/dispatch .claude/skills/dispatch`, run from the project root after creating .claude/skills/, adds it. Write it once; never copy or sync skills between harness directories. When .claude/skills/dispatch/ is a real directory rather than that link, it is the human's existing skill: offer to move it to .agents/skills/dispatch/ and leave the link in its place, show the diff against what you would write, and move or write nothing without an explicit yes.

Finish by handing off what you generated with kabane_handoff on the selected issue; when nothing is selected, first file one in this scope with kabane_add and hand off on the id it returns. The handoff names the files written, the overlays copied, each answer and whether the project's files or the human gave it, the gate commands and agents the skill uses, and, as not verified, any placeholder you had to fall back on.
